1. Abstract

This document specifies the rules an implementation of RGB applies when it reads invoices and validates consignments, for both RGB lines: v0.11 (RGB Protocol Association) and v0.12 (RGB-WG). Each rule comes with test vectors. The rules are data (rules/v011.jsonld, rules/v012.jsonld); §4 is generated from them, and the live suite runs every vector in your browser.

2. Status of this document

A living document, version 0.0.1, generated from source on each build. It is an independent community project, not affiliated with or endorsed by the RGB Protocol Association, RGB-WG or LNP/BP. It describes the rules as the reference crates implement them at the versions named in each rule, plus a few checks the rgbjs implementation adds (marked rgbjs). Where this document and the reference code disagree, the reference code is right and this document is wrong. It is early work: not for real funds.

3. Conformance

The key words MUST, MUST NOT, SHOULD and MAY are to be read as in RFC 2119.

Each rule has a level:

  • upstream: the reference code enforces it. A conforming implementation MUST reject input that violates it.
  • rgbjs: the reference code doesn't enforce it, but accepting such input is unsafe or misleading. A conforming implementation SHOULD reject it.
  • informative: such input can be valid, but it is not the same as the original. A conforming implementation MAY accept it but MUST NOT report it as the original: its result MUST show a different contract ID, an untrusted issuer, or different terminals, witnesses or state.

An implementation conforms if, for every vector in §5, its verdict matches: accept, reject, or for informative vectors reject or visibly different. Error messages are shown but not compared, so implementations may word them differently. Implementations MUST NOT crash on any vector: a decode error is a verdict, an abort is not.

4.2.2 Consignment files v0.12

Reading a binary consignment: the 8-byte magic RGBCNSGN, a 2-byte file version, a consignment version byte, the contract ID, then the strict-encoded consignment.

RuleRequirementLevelError and sourceVectors
v012-file-headerA consignment file starts with RGBCNSGN and file version 0, followed by consignment version 0. Later versions are rejected, not guessed at.
bytes[0..8] == "RGBCNSGN" ∧ file_version == 0 ∧ consign_version == 0		upstreambinfile magic/version error; DecodeError("unsupported future consignment version")
rgb-std 0.12.0-rc.3 src/contracts.rs:657 (CONSIGN_MAGIC_NUMBER), src/consignment.rs:124 (parse_consignment)		36
v012-strict-decodingThe body is strict-encoded: maps and sets are sorted with no duplicates, enum and union tags are known, identifiers are valid, strings are UTF-8, reserved bytes have their defined value, and the data doesn't end early.
strict_decode(body) succeeds ∧ encoding is canonical		upstreamDecodeError (DataIntegrityError, BrokenMapOrder, BrokenSetOrder, RepeatedMapValue, RepeatedSetValue, EnumTagNotKnown, UnionTagNotKnown, Utf8, Io UnexpectedEof)
strict_encoding 2.9.1 src/error.rs		36
v012-bounded-allocationA decoder must not allocate memory in proportion to a length it read from the data before checking it. Upstream strict_encoding and strict_types 2.9.1 pre-allocate from such lengths, so one corrupted byte can request about 4.4 GB (aborting a wasm or memory-limited process) or overflow capacity and panic. The pinned rgb-wallet 0.12.0-rc.3 crashes on rgb accept of such a file. A corrupted length must give a decode error or a verdict, never a crash.
∀ forged length: decode returns an error, never aborts		rgbjsDecodeError or a verdict (instead of an out-of-memory abort or capacity-overflow panic)
strict_encoding 2.9.1 src/embedded.rs:514 and strict_types 2.9.1 src/value/decode.rs:91 (Vec::with_capacity(len)); fixed in rgbjs rust/patches/		4

4.2.3 Articles and issuer trust v0.12

A v0.12 consignment carries its articles: the codex (which the contract ID commits to) and the semantics (APIs, types, libraries), which the contract ID does not commit to.

5. Test vectors

784 vectors (vectors/index.json), all copied into this repository; nothing is fetched at runtime.

  • 51 invoice vectors. Every case in the invoice tests of rgb-invoicing 0.11.1 and sonic-callreq 0.12.0, real invoices printed by rgb-cmd 0.11.1 and rgb-wallet 0.12.0-rc.3, and each of those given to the other line's parser.
  • 22 consignments. Contracts and transfers for every v0.11 schema (NIA, CFA, UDA, IFA, PFA) and for the v0.12 RGB20, RGB21 and RGB25 issuers. They come from the pinned CLIs and from offline generators that drive the reference wallet libraries (v0.11, v0.12). Files named created-*.rgb were made by rgbjs's own issueContract from fixed parameters, so creating is held to the same rules. Files named *.invalid.rgb must be rejected as they are, such as a PFA transfer without its issuer signature.
  • 711 corruptions. Every single-byte change (one bit flipped) of each consignment was run through the reference code and classified by the rule it breaks; up to three per rule and file are kept as vectors. No corruption is accepted as the same contract with the same result.
